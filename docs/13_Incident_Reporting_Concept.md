# ระบบแจ้งเหตุการณ์และการรวมรายงาน

> **สถานะ:** สเปก MVP ที่ยืนยันเมื่อ 24 กันยายน 2026

## หลักคิด

ระบบแยกข้อมูลเป็นสองระดับ:

- **Incident Report** คือข้อมูลดิบที่ Community User ส่งหนึ่งครั้ง ข้อความของทุกคนต้องเก็บแยกกันเสมอ
- **Incident** คือเหตุการณ์หลักบนแผนที่ ซึ่งรวม Incident Report ที่ยืนยันว่าอ้างถึงเหตุเดียวกันแล้ว

ตัวอย่าง Incident น้ำท่วมหนึ่งรายการอาจมี Report ว่า “น้ำเริ่มท่วมแล้ว”, “รถเล็กผ่านไม่ได้” และ “น้ำสูงขึ้นเรื่อย ๆ” หลายข้อความเหล่านี้ไม่ถูกเขียนทับหรือรวมเป็นข้อความเดียว

## การส่ง Report

Community User ดูข้อมูลสาธารณะได้โดยไม่ต้องเข้าสู่ระบบ แต่ต้องเข้าสู่ระบบก่อนส่ง Report ระบบตรวจรายละเอียดอย่างน้อย 5 ตัวอักษร พิกัดจุดเกิดเหตุ และจำกัดการส่งต่อบัญชีเพื่อลดสแปม รูปหรือวิดีโอเป็นข้อมูลเสริม

ผู้ใช้พิมพ์สิ่งที่พบได้อิสระ แล้วเลือก **Incident Type** ได้แต่ไม่บังคับ หน้า Report แสดง Quick Type ที่มาจาก catalog ในฐานข้อมูล และเปิด modal เพื่อดู Type ทั้งหมดโดยจัดกลุ่มตาม Category ผู้ใช้ไม่ต้องเลือก Category เอง

ข้อความที่ผู้ใช้พิมพ์ถูกเทียบกับ `tb_incident_keywords` เพื่อเสนอ Type เท่านั้น ระบบต้องไม่ถือคำแนะนำเป็น Type จริงจนกว่าผู้ใช้จะกดเลือก จึงเก็บค่าทั้งสามแยกกัน:

- `system_suggested_type_id` คือ Type ที่ keyword แนะนำ
- `user_selected_type_id` คือ Type ที่ผู้ใช้เลือก
- `final_type_id` คือ Type ที่ยืนยันใช้กับ Incident และการแสดงผล

เมื่อเปิดหน้า Report ระบบโหลด Type และ keyword ที่ active จาก Database ผ่าน API หนึ่งครั้งเก็บไว้เฉพาะใน memory ของหน้านั้น ระหว่างพิมพ์จึงค้นหาจาก cache หลัง trim ข้อความและไม่สนตัวพิมพ์เล็ก–ใหญ่สำหรับภาษาอังกฤษ: ถ้าพิมพ์ keyword ครบใช้ `includes()` และถ้ายังพิมพ์ไม่จบใช้ prefix ของข้อความหรือคำท้ายที่กำลังพิมพ์กับ keyword การจับคู่เริ่มที่ 2 ตัวอักษรเพื่อไม่ให้กว้างเกินไป โดยรวม keyword ที่ชี้ Type เดียวกันให้แสดง Type เดียว และแสดงได้สูงสุด 3 Type การ reload หน้าโหลด snapshot ใหม่เสมอ หาก API นี้ล้มเหลว ผู้ใช้ยังพิมพ์และส่ง Report ได้ เพียงไม่มีคำแนะนำ Type

ไม่มีช่อง Custom Report Type ใน flow MVP ผู้ใช้ใช้ข้อความอิสระเพื่ออธิบายสิ่งที่พบ และไม่เลือก Type ได้

## กติกาการจับคู่แบบง่าย

MVP ไม่ใช้คะแนน, AI, Machine Learning หรือ threshold หลายระดับ การจับคู่ใช้เพียงค่าที่ตั้งค่าได้หนึ่งชุด: **ระยะไม่เกิน 300 เมตร** และ **เวลาห่างไม่เกิน 30 นาที**

### ผู้ใช้เลือก Type และข้อความไม่ขัดกัน

ระบบค้นหา Incident ที่ยัง `active` และผ่านครบทุกข้อ:

1. Type เดียวกัน
2. จุดรายงานอยู่ในระยะที่กำหนด
3. เวลาของ Report ล่าสุดอยู่ในช่วงที่กำหนด

ถ้าครบ ระบบ auto-merge โดยผูก Report ใหม่กับ `incident_id` เดิม เพิ่ม `report_count` และอัปเดตเวลารายงานล่าสุด โดยคงตำแหน่ง ชื่อ Type และพื้นที่ผลกระทบของ Incident เดิมไว้

ถ้าไม่ครบทุกข้อ ระบบสร้าง Incident ใหม่ Type เดียวกันไม่ได้หมายความว่าเป็นเหตุเดียวกันเสมอ เช่น น้ำท่วมที่ห่างกัน 5 กิโลเมตรต้องเป็น Incident คนละรายการ

### ผู้ใช้ไม่เลือก Type

Report มี `final_type_id = NULL` และ `report_status = pending` จึงห้าม auto-merge

- ถ้าพบ Incident ที่ยัง `active` ในระยะและเวลาที่กำหนด ระบบสร้าง **Report Candidate** ไปยัง Incident ที่ใกล้ที่สุด
- ถ้าไม่พบ Incident แต่พบ Report ที่ไม่มี Type ในระยะและเวลาที่กำหนด ระบบสร้างหรือเพิ่ม **Candidate Group**
- ถ้าไม่พบอะไรใกล้เคียง Report เป็นรายการเดี่ยวแบบ `pending`

ทุกกรณีข้างต้นยังแสดงเป็น **Generic Marker พร้อม Badge “รอตรวจสอบ”** บน Public Map ได้ ไม่มีรัศมี และ Report ไม่ถูก merge ก่อน Administrator ยืนยัน

### ข้อความกับ Type ที่ผู้ใช้เลือกขัดกัน

ถ้าระบบแนะนำ “น้ำท่วม” จากข้อความ แต่ผู้ใช้ยืนยัน “ไฟไหม้” หน้า Report ต้องเตือนก่อนส่ง ผู้ใช้เปลี่ยนเป็น Type ที่แนะนำหรือยืนยัน Type เดิมก็ได้

เมื่อผู้ใช้ยืนยัน Type ที่ขัดกัน Report จะเป็น `type_status = conflict` และ `report_status = pending` ไม่ auto-merge, ไม่ใช้ Type นั้นวาดรัศมี และแสดงเป็น Generic Marker เพื่อให้ Administrator ตรวจสอบ

## Candidate ไม่ใช่ Merge

Candidate หมายถึง “ระบบสงสัยว่าอาจเป็นเหตุเดียวกัน” ไม่ใช่การรวม Report หรือสร้าง Incident เดียวทันที

Candidate Group เก็บสมาชิกเป็น Report หลายแถว เช่น A, B และ C ยังคงมีข้อความ เวลา พิกัด และ media ของตนเอง เมื่อ Administrator ยืนยัน จึงเลือกหรือสร้าง Incident, กำหนด Type แล้วผูก Report ที่ยืนยันเข้ากับ Incident นั้น

Report หนึ่งรายการอยู่ Candidate Group ได้ไม่เกินหนึ่งกลุ่ม กลุ่มใช้ Report แรกเป็นจุดอ้างอิง และสมาชิกทุกคนต้องผ่านระยะกับเวลาชุดเดียวกัน เพื่อป้องกันการเชื่อมต่อเป็นทอด ๆ จนกลุ่มใหญ่เกินจริง

ถ้า Report ที่ไม่มี Type อยู่ใกล้ Incident หลายรายการ ระบบเลือก Incident ที่ใกล้ที่สุดเป็น Candidate เดียว; หากระยะเท่ากันให้เลือก Incident ที่มี Report ล่าสุดใหม่กว่า

## หน้าที่ Administrator

Administrator เห็น Report Candidate, Candidate Group และ Report เดี่ยวที่ `pending` พร้อมข้อความ พิกัด เวลา media, Type ที่ระบบแนะนำ และ Type ที่ผู้ใช้เลือก

Administrator สามารถกำหนด Type ให้ Report ที่ `pending` ได้ เมื่อตัดสินแล้วระบบใช้ Type, เวลาส่งเดิม และตำแหน่งเดิมตรวจ Incident Matching ชุดเดิม: ถ้าเจอ Incident ที่เข้าเงื่อนไขให้ merge และถ้าไม่เจอให้สร้าง Incident ใหม่ นอกจากนี้ Administrator ยืนยัน Candidate, ปฏิเสธ Report เดี่ยว, แก้ Candidate ที่จับคู่ผิด และแยก Report ออกจาก Incident ได้เมื่อ auto-merge ผิด

สถานะมีสองระดับและห้ามปนกัน:

- Report ใช้ `pending`, `verified`, `rejected`
- Incident ใช้ `active`, `resolved`

`incident_id` บอกความเป็นสมาชิกของ Incident ส่วน Candidate เป็นความสัมพันธ์สำหรับการตรวจสอบ ไม่ใช่ Report Status

## การแสดงผลบนแผนที่

Type เป็นผู้กำหนด icon, `display_mode` และ `default_radius_m`

- `marker` แสดงหมุดหรือ icon ไม่มีรัศมี
- `nearby` แสดงหมุดหรือ icon พร้อมพื้นที่แจ้งเตือนใกล้เคียง
- `area` แสดงหมุดหรือ icon พร้อมพื้นที่ผลกระทบโดยประมาณ
- ไม่มี Type หรือ Type ขัดกับข้อความ แสดง Generic Marker พร้อมสถานะรอตรวจสอบ ไม่มีรัศมี

พื้นที่ผลกระทบเป็นเพียงค่าประมาณตาม Type ไม่ใช่ขอบเขตอันตรายที่แม่นยำ 100% และไม่คำนวณจาก Severity

Public Map โหลดข้อมูลจาก API สำหรับแผนที่เป็นสองชุดแยกกัน: `incidents` สำหรับ Incident ที่ยืนยันเป็นเหตุการณ์หลักแล้ว และ `pending_reports` สำหรับ Report ที่ยังไม่มี Incident ทุก `pending_reports` แสดงเป็น Generic Marker พร้อมสถานะ “รอตรวจสอบ” เท่านั้น แม้ระบบจะสร้าง Candidate หรือ Candidate Group ไว้หลังบ้านแล้วก็ตาม

Preset รัศมีของ Type ใน MVP ใช้เพื่อการแสดงผลโดยประมาณบน Public Map:

| การแสดงผล | Incident Type |
|---|---|
| Marker only | ถนนชำรุด, ขยะ / ของเสีย, พบสัตว์เลี้ยง, ของหาย, พบของ, สิ่งกีดขวางพื้นที่สาธารณะ |
| 200 เมตร | เสาไฟล้ม, สายไฟขาด, ท่อน้ำแตก |
| 300 เมตร | รถเสียกีดขวาง, เหตุทะเลาะวิวาท |
| 500 เมตร | รถชน, รถคว่ำ, ถนนถูกกีดขวาง, สะพานเสียหาย, ไฟไหม้อาคาร, อาคารเสียหาย / ถล่ม, วัตถุต้องสงสัย, สัตว์อันตราย |
| 1000 เมตร | ควันผิดปกติ, กลิ่นสารเคมี, สารเคมีรั่วไหล, ดินถล่ม, เหตุไฟไหม้อื่น ๆ |
| Search area 1000 เมตร | สัตว์เลี้ยงหาย |
| Search area 2000 เมตร | บุคคลสูญหาย |
| 3000 เมตรโดยประมาณ | น้ำท่วม, น้ำป่าไหลหลาก |
| ไม่ใช้ Fixed Radius | พายุ, แผ่นดินไหว, ภัยแล้ง, PM2.5 / ฝุ่น, มลพิษทางอากาศ, ไฟฟ้าดับ, น้ำประปาขัดข้อง, สึนามิ |

## ตารางหลัก

| ตาราง | หน้าที่ |
|---|---|
| `tb_incident_categories` | จัดกลุ่ม Incident Type ในหน้าจอเลือก Type |
| `tb_incident_types` | Type, icon, display mode, พื้นที่ผลกระทบ และ Quick Type |
| `tb_incident_keywords` | keyword สำหรับแนะนำ Type |
| `tb_incident_reports` | Report ดิบของผู้ใช้; `incident_id` เป็น `NULL` ได้ |
| `tb_incident_media` | รูปและวิดีโอของ Report |
| `tb_incidents` | เหตุการณ์หลักบนแผนที่ |
| `tb_incident_report_candidates` | Candidate จาก Report ที่ไม่มี Type ไปยัง Incident |
| `tb_incident_candidate_groups` | กลุ่ม Report ที่ไม่มี Type และอยู่ใกล้กัน |
| `tb_incident_candidate_group_reports` | สมาชิก Report ของ Candidate Group |

Trust Score เก็บเป็น snapshot เพื่อใช้ประเมินความน่าเชื่อถือในอนาคต แต่ห้ามใช้ตัดสินว่า Report สองรายการเป็นเหตุเดียวกัน
