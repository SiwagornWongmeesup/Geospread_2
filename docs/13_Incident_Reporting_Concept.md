# 13 — แนวคิดการรับและจัดการรายงานเหตุการณ์

> **สถานะ:** ตกลงใช้เป็นแนวคิดผลิตภัณฑ์ ณ วันที่ 21 กันยายน 2026
>
> เอกสารนี้กำหนด workflow ของ Incident Report ก่อนนำไปเปลี่ยน schema, API หรือ UI จริง

## หลักคิด

GeoSpread ให้ Community User บอกสิ่งที่ตนเห็นด้วยภาษาของตนเองก่อน แล้วให้ระบบช่วยจัดประเภท ประเมิน และเลือกวิธีแสดงผลเท่าที่ข้อมูลรองรับ ผู้ใช้ต้องส่งรายงานได้ แม้ระบบจะยังไม่รู้จักประเภทนั้น

## Workflow การรับรายงาน

1. ผู้ใช้กรอกข้อความอิสระในช่อง **เกิดอะไรขึ้น?** พร้อมตำแหน่ง; รูปภาพหรือวิดีโอเป็นข้อมูลเสริม
2. ระบบจับ keyword เพื่อเสนอ **Suggested Incident Type** ที่ใกล้เคียง เช่น “รถชน” → “อุบัติเหตุทางถนน”, “น้ำท่วมหน้าตลาด” → “น้ำท่วม”, “ฝุ่นเยอะ” → “PM2.5 / ฝุ่นละออง”
3. ผู้ใช้เลือกยอมรับคำแนะนำหรือข้ามได้เสมอ และระบุ **Custom Report Type** ของตนเองได้
4. ระบบบันทึกเป็น **Incident Report** โดยไม่บังคับว่าต้องเป็นประเภทมาตรฐาน และให้สถานะเริ่มต้นเป็น **รอตรวจสอบ**
5. ระบบอาจเชื่อม Report เข้ากับ **Incident** หลักเดิม หรือสร้าง Incident หลักใหม่ แล้วจึงตรวจความน่าเชื่อถือและประเมินความรุนแรงภายหลัง

ระยะแรกใช้ deterministic keyword matching เท่านั้น ไม่ต้องพึ่ง AI ซับซ้อน; AI classification เป็นความสามารถเสริมในอนาคตและต้องไม่บังคับแทนผู้ใช้

Suggested Incident Type ต้องเป็นคำแนะนำแบบไม่ขวางการส่งรายงาน: ระบบไม่อาจเปลี่ยนคำแนะนำเป็น Type ที่ผู้ใช้เลือกเองโดยอัตโนมัติ ผู้ใช้เลือกได้จากชิปใต้ Reported Observation หรือกด “ดูประเภทเพิ่มเติม” เมื่ออยากค้นหาเองเท่านั้น หากไม่เลือก ระบบเก็บคำแนะนำไว้ได้ แต่ตอนสร้างรายงาน `user_selected_type_id` และ `final_type_id` ต้องยังว่าง และแผนที่แสดง marker สีแดงสถานะรอตรวจสอบโดยไม่มีรัศมี

### การเลือก Type ใน UI

หน้ารายงานเสนอ **Type โดยตรง** จากข้อความที่ผู้ใช้พิมพ์ เช่น “น้ำท่วมหน้าตลาด” → ปุ่มแนะนำ “น้ำท่วม” ผู้ใช้กด Type ที่ตรง แล้วระบบจึงรู้ Category ของ Type นั้นเอง ผู้ใช้ไม่ต้องเลือก Category ซ้ำ

Category มีหน้าที่จัดระเบียบ Type เท่านั้น และแสดงเมื่อผู้ใช้กด “ดูประเภทเพิ่มเติม” หรือหา Type ที่ตรงไม่พบ โดย UI จะแสดง Type แบ่งตาม Category ใน modal หรือหน้าสำหรับเลือกเพิ่มเติม

เมื่อผู้ใช้เลือก Type จากโมดัล ระบบต้องนำ Type ที่เลือกขึ้นเป็นรายการแรกในส่วน “เหตุการณ์ที่ระบบแนะนำ” ทันที แล้วจึงแสดงคำแนะนำอื่นที่มาจากข้อความรายงานหรือค่าเริ่มต้นตามลำดับ

เมื่อผู้ใช้ยืนยัน Type ระบบอ่าน `display_mode` และ `default_radius_m` ของ Type นั้น: `marker` แสดง Marker + Icon อย่างเดียว, `nearby` แสดง Marker + Icon + พื้นที่แจ้งเตือนใกล้เคียง, และ `area` แสดง Marker + Icon + พื้นที่ผลกระทบโดยประมาณ Type—not Category หรือ Severity—เป็นผู้กำหนดว่าจะวาดรัศมีหรือไม่และวาดเท่าไร

### Flow ฐานข้อมูลของการรับรายงาน

1. ผู้ใช้พิมพ์ว่าเกิดอะไรขึ้น
2. ระบบ match ข้อความกับ `tb_incident_keywords`
3. Keyword ชี้ไปยัง `tb_incident_types` และระบบเสนอ Type ให้ผู้ใช้
4. ผู้ใช้เลือก Type ที่ตรง; ระบบรู้ Category จาก `tb_incident_types.category_id` โดยอัตโนมัติ
5. ระบบบันทึกลง `tb_incident_reports`: Type ที่ระบบเสนอเก็บใน `system_suggested_type_id`, Type ที่ผู้ใช้เลือกเก็บใน `user_selected_type_id`, และ Type ที่ระบบ/ผู้ดูแลยืนยันใช้จริงเก็บใน `final_type_id`
6. หากมีรูปหรือวิดีโอ ระบบสร้างแถวใน `tb_incident_media` แล้วผูกด้วย `report_id`
7. ระบบค้นหา `tb_incidents` ที่ยัง active ด้วย Type เดียวกัน ตำแหน่ง และเวลา
8. ถ้าพบ Incident เดิมที่ตรงเกณฑ์ ระบบใส่ `incident_id` เดิมใน Report; หากไม่พบ สร้าง Incident ใหม่แล้วใส่ `incident_id` นั้นใน Report

ดังนั้น Report ใหม่ของเหตุซ้ำจะไม่สร้าง `tb_incidents` ใหม่ทุกครั้ง แต่เชื่อมเข้ากับ Incident หลักเดิมผ่าน `tb_incident_reports.incident_id`

## กติกาการแสดงผลบนแผนที่

| สภาพของรายงาน | การแสดงผลเริ่มต้น |
|---|---|
| ผู้ใช้ระบุเหตุที่ระบบยังไม่รู้จัก หรือไม่ยอมรับ Suggested Incident Type | Marker พร้อมสถานะรอตรวจสอบ ไม่มีรัศมี |
| ระบบหรือผู้ใช้ยืนยันประเภทมาตรฐานที่มี `Map Display Mode = marker` | Marker / icon ตามประเภท ไม่มีรัศมี |
| ประเภทมาตรฐานที่มี `Map Display Mode = icon + impact radius` | Icon ตามประเภทพร้อม Impact Radius |
| ประเภทที่อนาคตรองรับพื้นที่ผลกระทบ | พื้นที่ผลกระทบโดยประมาณตามกติกาของประเภท |

Impact Radius เป็นค่าเริ่มต้นที่ระบบกำหนดตาม Type มาตรฐาน ไม่คำนวณจาก Category หรือ Severity Level และ Administrator อาจปรับเฉพาะเหตุภายหลังได้

## ประเภทที่ไม่รู้จักและการขยายระบบ

รายงานที่ไม่ตรงกับ Incident Type มาตรฐานยังต้องรับได้ในฐานะ Custom Report Type ระบบแสดง marker รอตรวจสอบและเก็บข้อความดังกล่าวเป็นข้อมูลเรียนรู้เพื่อพิจารณาเพิ่ม Type มาตรฐานในอนาคต จึงไม่ควรบังคับให้ผู้ใช้เลือกหมวดที่ไม่ตรงกับเหตุที่พบ รายการทรัพย์สินสูญหายและสัตว์เลี้ยงสูญหายเป็น Incident Type มาตรฐานแล้ว

## ความน่าเชื่อถือและความรุนแรง

**Credibility** ตอบว่า “เรามั่นใจแค่ไหนว่าเหตุเกิดขึ้นจริง” โดยใช้ข้อมูลเช่น รายงานจากหลายคน ความใกล้ของผู้รายงาน รูปหรือวิดีโอ ประวัติผู้รายงาน และการตรวจสอบของ Administrator

**Severity Level** ตอบว่า “เหตุส่งผลกระทบรุนแรงแค่ไหน” และประเมินภายหลังจากผลกระทบ จำนวนผู้ได้รับผลกระทบ ผู้บาดเจ็บ สภาพถนน การอพยพ การขยายตัวของเหตุ และการตรวจสอบของชุมชนหรือ Administrator

สองค่านี้เป็นอิสระต่อกัน: รายงานน้ำท่วมเล็กน้อยจากคนจำนวนมากอาจมี Credibility สูง แต่ Severity ต่ำได้ Community User ไม่เลือก Severity Level ในฟอร์ม

Severity ใช้กับ priority, การเรียงฟีด, ระดับการแจ้งเตือน และการเน้นใน UI โดยใช้ badge, icon, border หรือแถบเล็กน้อยแทนการทำทั้งการ์ดเป็นสีแรง: ต่ำ = เทา/ฟ้าอ่อน, ปานกลาง = เหลือง, สูง = ส้ม, วิกฤต = แดง

## แบบจำลองข้อมูลและการรวม Report

ตารางหลักสำหรับ MVP คือ `tb_incident_categories` (หมวดใหญ่), `tb_incident_types` (ประเภทที่กำหนด logic/icon/radius), `tb_incident_keywords` (คำแนะนำ Type), `tb_incident_reports` (ข้อมูลดิบที่ผู้ใช้ส่ง), `tb_incident_media` (รูปหรือวิดีโอของ Report) และ `tb_incidents` (เหตุหลักที่รวม Report)

Report ใหม่จะค้นหา Incident ที่มี `incident_status = active` ก่อน แล้วให้คะแนนการจับคู่แบบ deterministic:

- Type เดียวกัน: 40 คะแนน
- จุดเกิดเหตุห่างไม่เกิน 300 เมตร: 35 คะแนน
- เวลารายงานห่างไม่เกิน 30 นาที: 25 คะแนน

คะแนน 80–100 รวมเข้า Incident เดิมอัตโนมัติ, 50–79 เก็บเป็น candidate เพื่อรอข้อมูลหรือการตรวจสอบ, และต่ำกว่า 50 สร้าง Incident ใหม่ ใน MVP ให้ Type ตรงกันเฉพาะ `type_id` เดียวกันเท่านั้น; Report ที่ไม่มี Type มาตรฐานไม่ auto-merge รายงานที่รวมแล้วเก็บ `incident_id`, เพิ่ม `report_count` และอัปเดต `last_reported_at` ของ Incident

Administrator ต้องแยก Report ออกจาก Incident ได้ภายหลังเมื่อระบบรวมผิด เช่น รถชนสองจุดที่อยู่ใกล้กันและเกิดเวลาเดียวกัน

สถานะของสองระดับแยกจากกัน: Report ใช้ `submitted`, `pending`, `linked`, `suspicious`, `rejected`; Incident ใช้ `incident_status` เป็น `active`, `resolved`, `closed` และ `verification_status` เป็น `unverified`, `verified`

## ขอบเขตการเปลี่ยนแปลงภายหลัง

ก่อนพัฒนา feature จริง ต้องปรับ schema/API เพื่อรองรับข้อความอิสระ, Suggested Incident Type, Custom Report Type, Credibility, Severity ที่ประเมินภายหลัง และ Map Display Mode / Impact Radius ตาม [ADR-0001](./adr/0001-flexible-incident-intake-and-map-display.md) เอกสารนี้ไม่อนุญาตให้เปลี่ยน migration หรือ endpoint โดยอัตโนมัติ
