# โครงสร้างโฟลเดอร์ Backend แบบ Full-stack มาตรฐาน (3-Tier Architecture)

เอกสารนี้ใช้อ้างอิงสำหรับการจัดโครงสร้างโค้ดในโปรเจกต์ GeoSpread (Backend) เพื่อแยกหน้าที่การทำงาน (Separation of Concerns) ให้ชัดเจน โค้ดอ่านง่าย และดูแลรักษาได้ในระยะยาว

## โครงสร้างโฟลเดอร์หลัก

```text
backend/
├── src/                    # โค้ดหลักของแอปพลิเคชัน
│   ├── config/             # ตั้งค่าต่างๆ (ดึงจาก .env)
│   ├── controllers/        # รับ Request และส่ง Response
│   ├── middlewares/        # ดักจับและตรวจสอบก่อนถึง Controller
│   ├── repositories/       # คุยกับ Database - ยิง SQL เท่านั้น
│   ├── routes/             # กำหนด Endpoint API
│   ├── services/           # 🧠 Business Logic ทั้งหมดอยู่ที่นี่
│   ├── utils/              # ฟังก์ชันช่วยเหลือที่ใช้ซ้ำได้
│   └── validators/         # ตัวตรวจสอบข้อมูลที่ส่งเข้ามา (Request Schema)
├── db/                     # ไฟล์ Migration หรือ Schema SQL ของฐานข้อมูล
├── .env                    # ไฟล์เก็บความลับ (ไม่เอาขึ้น Git)
└── webserver.js            # ไฟล์เริ่มต้นรัน Server (Entry point)
```

---

## หน้าที่ของแต่ละโฟลเดอร์ (Layer)

### 1. `routes/` (ผู้บอกทาง)
*   **หน้าที่:** กำหนด URL Path (Endpoint) และจับคู่กับ HTTP Method (GET, POST, PUT, DELETE) จากนั้นส่งต่อไปให้ Controller เป็นผู้จัดการ
*   **ตัวอย่าง:** `router.get('/users', userController.getAllUsers);`

### 2. `controllers/` (ผู้รับแขก)
*   **กฎเหล็ก:** **ห้ามเขียน Business Logic ยาวๆ ที่นี่เด็ดขาด** (ตามกฎใน `AGENTS.md`)
*   **หน้าที่:** 
    *   รับค่าจาก Client (เช่น `req.body`, `req.params`)
    *   ส่งค่าไปให้ `services/` ช่วยคิดและประมวลผล
    *   นำผลลัพธ์ที่ได้มาจัดรูปแบบ (JSON) และตอบกลับไปยัง Client ด้วย HTTP Status ที่เหมาะสม (เช่น 200, 400, 500)

### 3. `services/` (ผู้จัดการ / 🧠 Business Logic)
*   **หน้าที่:** ตรรกะของแอปพลิเคชันทั้งหมดอยู่ที่นี่! 
    *   ประมวลผลข้อมูล, ตรวจสอบเงื่อนไขทางธุรกิจ
    *   เรียกใช้งาน `repositories/` เพื่อเซฟ/ดึงข้อมูลจากฐานข้อมูล
    *   เตรียมข้อมูลให้พร้อมก่อนส่งกลับไปที่ Controller
*   **ข้อดี:** โค้ดใน Service สามารถถูกเรียกใช้ซ้ำได้ (Reusability) ไม่ว่าจะเรียกผ่าน REST API หรือ WebSocket

### 4. `repositories/` (ผู้ประสานงานฐานข้อมูล)
*   **หน้าที่:** ทำหน้าที่ติดต่อกับ Database โดยตรง (ในโปรเจกต์นี้คือการยิง Raw SQL ผ่าน `pg`)
*   **ข้อสำคัญ:** มีหน้าที่แค่ SELECT, INSERT, UPDATE, DELETE โดยไม่ต้องสนใจว่าผลลัพธ์จะถูกเอาไปทำอะไรต่อ (ไม่มี Business Logic)

### 5. `middlewares/` (ยามรักษาการณ์)
*   **หน้าที่:** ดักจับ Request ก่อนที่จะไปถึง Controller 
*   **ตัวอย่าง:** ตรวจสอบ Token เข้าสู่ระบบ (Auth), ดักจับ Error รวม, เก็บ Log การใช้งาน

### 6. `validators/` (หรือ schemas)
*   **หน้าที่:** ตรวจสอบรูปแบบและความถูกต้องของข้อมูลที่ส่งเข้ามา (Input Validation) ก่อนที่จะส่งให้ Controller (เช่น เช็คว่าอีเมลถูกต้องไหม)

### 7. `config/` (ตั้งค่าระบบ)
*   **หน้าที่:** เก็บไฟล์โค้ด (.js) ที่ทำหน้าที่อ่านค่าจากไฟล์ความลับ (`.env`) เพื่อนำมาสร้างการเชื่อมต่อให้กับระบบ เช่น `database.js` 

### 8. `utils/` (เครื่องมือจิปาถะ)
*   **หน้าที่:** เก็บฟังก์ชันช่วยเหลือทั่วๆ ไปที่ไม่ผูกติดกับ Business Logic เช่น ฟังก์ชันสุ่มรหัสผ่าน, แปลงรูปแบบวันที่

## Workflow การไหลของข้อมูล (เมื่อถูกเรียก API)

1. `Client` ยิง Request เข้ามา
2. ➡️ **`routes/`** ตรวจสอบว่าตรงกับ Path ไหน
3. ➡️ **`middlewares/`** (ถ้ามี) ตรวจสอบสิทธิ์หรือความถูกต้อง
4. ➡️ **`controllers/`** รับข้อมูลและสั่งให้ Service ทำงาน
5. ➡️ **`services/`** คิดและประมวลผล (ถ้าต้องใช้ DB ก็จะเรียก Repository)
6. ➡️ **`repositories/`** ดึง/บันทึกข้อมูลกับ Database และส่งผลลัพธ์กลับให้ Service
7. ➡️ **`services/`** ส่งผลลัพธ์สุดท้ายกลับให้ Controller
8. ➡️ **`controllers/`** ตอบกลับ Response ให้ `Client`

## เกี่ยวกับไฟล์ `.env`
*   **หน้าที่:** เป็นแค่ไฟล์ข้อความธรรมดาที่เก็บรหัสผ่าน (เช่น `DB_PASSWORD=1234`)
*   **ห้าม** นำขึ้น Git เด็ดขาด (ต้องอยู่ใน `.gitignore`)
*   โค้ดในระบบจะดึงค่าจาก `.env` ผ่าน `process.env` โดยตรง หรือผ่านไฟล์ที่อยู่ในโฟลเดอร์ `config/`
